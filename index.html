Key concepts: Ray & KubeRay

The important pieces that make this project scale and self-heal.

Ray Serve

A scalable model-serving library. The agent is a Serve deployment wrapping FastAPI; each replica is a worker process handling requests.

replicas

KubeRay Operator

A Kubernetes controller that watches the RayService CR and creates/manages Ray pods (head + workers) to match the desired state.

operator pattern

Head & Worker pods

The head pod runs GCS, the dashboard, and the Serve controller. Worker pods run the Serve replicas that do the actual work.

pods

Two-layer autoscaling

Ray Serve adds replicas based on queue size first; the Ray autoscaler then adds worker pods; the cluster autoscaler adds nodes if pods can't fit.

autoscaling

Self-healing

If a pod dies, KubeRay/Kubernetes detects the gap and schedules a replacement so the service keeps serving — zero manual intervention.

resilience

Zero-downtime upgrades

A RayService brings up a new cluster, waits until it's ready, then shifts traffic — so deploys don't drop requests.

HA

Runbook

Deployment guide

Thirteen steps from an empty AWS account to a running agent. Tick each step as you finish it; progress is saved in this browser.

0 / 13 done
One-time setup
1

Create the Terraform state bucket

AWS Console
  1. S3 → Create bucket.
  2. Bucket name: kuberay-agent-tfstate-fde-ray (must be globally unique).
  3. Region: us-east-1 (same as AWS_REGION).
  4. Enable Bucket Versioning, then Create bucket.

Create the bucket in the same region as AWS_REGION (us-east-1). A mismatch causes a 301 … actual location error during terraform init.

2

Create the GitHub OIDC provider and IAM role

AWS Console

OIDC provider

  1. IAM → Identity providers → Add provider → OpenID Connect.
  2. Provider URL: https://token.actions.githubusercontent.com, audience sts.amazonaws.com → Add provider.

IAM role

  1. IAM → Roles → Create role → Web identity, choose the provider above and audience sts.amazonaws.com.
  2. Attach AdministratorAccess (lab only — scope down for production).
  3. Name it github-actions-deploy → Create role.

Trust policy

Open the role → Trust relationships → Edit trust policy and replace ACCOUNT_ID, GITHUB_ORG, REPO:

trust-policy.json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::ACCOUNT_ID:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
        },
        "StringLike": {
          "token.actions.githubusercontent.com:sub": "repo:GITHUB_ORG/REPO:*"
        }
      }
    }
  ]
}

Copy the role ARN for the next step.

3

Set GitHub repository variables

GitHub

Repo → Settings → Secrets and variables → Actions → Variables → New repository variable. None of these are secret.

Name Value
AWS_REGION region for the cluster, e.g. us-east-1
AWS_OIDC_ROLE_ARN role ARN from Step 2
TF_STATE_BUCKET kuberay-agent-tfstate-fde-ray

TF_STATE_KEY, CLUSTER_NAME and ECR_REPO are hardcoded in Terraform and the workflows.

GitHub Actions
4

Provision the infrastructure

GitHub Actions

Actions → infra Terraform → Run workflow, with action = apply.

Creates the VPC, EKS cluster YashAcademy, node group, ECR, bastion, Secrets Manager secret, KubeRay operator and External Secrets Operator. The run summary lists the bastion IP and ECR URL.

5

Add the Gemini API key

AWS Console
  1. Secrets Manager → kuberay-agent/gemini-api-key → Retrieve secret value → Edit.
  2. Replace CHANGE_ME under api-key with your real key → Save.

Terraform ignores later changes to this value, so re-running apply will not overwrite your key.

6

Build and push the image

GitHub Actions

Actions → deploy → Run workflow. It builds the React UI and Ray app image, pushes it to ECR, and commits the new image tag into k8s/kustomization.yaml.

Deploy and test
7

Connect to the bastion

Terminal
bash
ssh ec2-user@<BASTION_PUBLIC_IP>
aws eks update-kubeconfig --name YashAcademy --region us-east-1
8

Clone the repo and deploy

Bastion
bash
sudo yum install -y git          # if git is not already installed
git clone https://github.com/arumullayaswanth/Ray.git
cd Ray
git pull                         # picks up the image tag the deploy workflow committed
kubectl apply -k k8s/

Creates the namespace, service account, SecretStore, ExternalSecret, RayService and public Service.

9

Verify the rollout

Bastion
bash
kubectl get rayservice ai-agent -n ai-agent
kubectl get pods -n ai-agent
kubectl get secret gemini-secret -n ai-agent
kubectl get svc -n ai-agent

Wait for the RayService to be ready and for gemini-secret to exist before testing.

If gemini-secret is missing and pods show CreateContainerConfigError, External Secrets started before its Pod Identity was ready. Restart it once: kubectl rollout restart deployment -n external-secrets, wait ~30s, then re-check.

10

Port-forward (Ray dashboard + agent)

Bastion

The head service name has a random suffix, so look it up instead of hardcoding it. Run both forwards in the background so the terminal stays usable (do not use Ctrl+Z — it leaves the port bound).

bash
HEAD_SVC=$(kubectl get svc -n ai-agent -o name | grep head-svc)

# Ray dashboard on the bastion public IP (SG already allows all ports)
nohup kubectl port-forward --address 0.0.0.0 $HEAD_SVC 8265:8265 -n ai-agent > /tmp/pf8265.log 2>&1 &

# Agent serve API on localhost
nohup kubectl port-forward svc/ai-agent-serve-svc 8000:8000 -n ai-agent > /tmp/pf8000.log 2>&1 &
sleep 3; cat /tmp/pf8265.log /tmp/pf8000.log

Ray dashboard: http://<BASTION_PUBLIC_IP>:8265 · Agent: http://localhost:8000. If a port says "address already in use", clear it with sudo fuser -k 8265/tcp (or 8000/tcp) and retry.

11

Test the agent

Bastion
bash
# 1) single request — expect a JSON answer
curl -s -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"message":"hi"}'; echo

# 2) sustained load: 20 workers for 60s (builds a queue so Serve scales 1 -> 4)
end=$((SECONDS+60))
for w in $(seq 1 20); do
  ( while [ $SECONDS -lt $end ]; do
      curl -s -o /dev/null -X POST http://localhost:8000/chat \
        -H "Content-Type: application/json" \
        -d '{"message":"write a 5 line poem about the cloud"}'
    done ) &
done
wait; echo done

Watch the Ray dashboard Serve tab: the Agent replicas climb 1 → 4 within ~20s, then drop back to 1 about 10s after the load stops. A short one-shot loop finishes too fast to trigger scaling — the 60s sustained load is what builds the queue.

12

Get the public URL (optional)

Bastion
bash
kubectl get svc ai-agent-public -n ai-agent \
  -o jsonpath='{.status.loadBalancer.ingress[0].hostname}'

/chat has no authentication and the Service allows 0.0.0.0/0. Restrict loadBalancerSourceRanges before sharing the URL.

Clean up
13

Tear everything down

GitHub Actions

Actions → infra Terraform → Run workflow with action = destroy. It deletes the Kubernetes app and NLB first, then runs terraform destroy.

bash · manual equivalent
kubectl delete -k k8s/          # removes the app + NLB
cd terraform && terraform destroy

The S3 state bucket and the GitHub OIDC role are created manually and are not deleted. Remove them by hand for a true $0 bill.
